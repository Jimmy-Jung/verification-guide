# 검증 원칙과 해석 원칙

## 차례
- 검증 원칙 4개
- 해석 원칙 7개
- "0건" 문구 규칙
- 판정 기준 출처 규칙
- 반복 횟수 기본값
- 결론의 신뢰도 표기

## 검증 원칙 4개

1. **출처가 아니라 결과.** 작성 주체(사람·AI·외주)는 입력에서 어떻게 동작하는지 알려주지 않는다. 질문을 "어떤 입력에서 크래시·오표시·끊김·보안 문제가 생기는가"로 바꾸고 네 질문(Q1~Q4)으로 고정한다.
2. **다시 실행할 수 있어야 한다.** 테스트·벤치마크·정적 분석을 스크립트로 고정한다. 빠르고 결정적인 검사는 커밋마다, 실기기·계측·UI 검사는 릴리스 전 수동으로 나눈다. 실기기 값은 다시 재면 흔들리므로 "같은 숫자"가 아니라 "같은 판정"이 나오는지 본다.
3. **수치의 단일 출처.** 원시 결과(벤치 JSON·커버리지·정적 분석 결과·결함 대장)를 집계 스크립트가 CSV로 모으고, 그래프는 CSV만 읽는다. 본문 표는 CSV에서 옮기고 출처를 적는다. 여러 번 잰 값 중 유리한 값만 고를 여지를 없앤다.
4. **발견에서 회귀 고정까지.** 결함을 찾으면 ① 가장 짧은 재현 입력 ② 원인 수정 ③ 그 입력을 회귀 테스트 입력 또는 수정 전에 실패하는 테스트로 저장 ④ 전체 재실행. 회귀 입력은 커밋마다 CI에서 다시 검사한다.

## 해석 원칙 7개

1. **중앙값과 범위.** 대푯값은 평균이 아니라 중앙값. 최소–최대 범위를 함께 적는다. 중앙값은 보통의 실행, 범위는 가장 나빴던 실행을 말한다. 범위가 판정 구간 여러 개에 걸치면 중앙값 하나로 판정하지 않는다.
2. **반복 횟수의 근거.** 3회는 한 번 튄 값에 중앙값이 끌려가지 않는 최소 횟수이고 범위의 신뢰도는 낮다. 1회 값끼리의 비교는 결론으로 쓰지 않는다. 빌드 비교는 같은 날 같은 기기에서 번갈아 6회 이상.
3. **실기기 Release 절댓값, 시뮬레이터 Debug 상대값.** Debug는 최적화가 꺼져 있고 시뮬레이터는 호스트 CPU에서 돈다. 그 값은 "이전보다 느려졌나"에만 쓴다. 출시 연도·칩 세대가 다른 두 기기의 값을 플랫폼 우열로 읽지 않는다.
4. **외부 기준과 회귀 방지 기준.** 플랫폼 제작사·공식 문서의 기준을 먼저 찾아 인용하고 어느 기준인지 함께 말한다. 프로젝트가 정한 값(커버리지 기준, 시간 상한, CI 게이트 임계값)은 "사용자에게 충분히 빠르다"의 근거가 아니라 "나빠지면 CI를 실패시킨다"는 장치로 읽는다.
5. **"0건"의 범위.** 아래 규칙.
6. **정의가 다른 지표의 비교 금지.** 다른 도구·다른 정의의 두 값을 "두 배 느리다"처럼 읽지 않는다. 각각을 자기 기준과만 비교한다. 플랫폼이 다른 지표는 판정표에서 각자의 기준 옆에만 둔다.
7. **원리가 다른 도구의 교차 확인.** 핵심 지표는 표본 추출·구간 기록·반복 측정처럼 오차 방식이 다른 도구 두세 개로 같은 구간을 잰다. 1% 안에서 맞으면 한 도구의 버릇이 아니다. 값이 상식과 어긋나면 그 자체가 신호다(예: 측정 구간 길이에 가까운 inclusive 시간은 추정치일 가능성).

## "0건" 문구 규칙

"0건"은 반드시 도구의 시야를 붙여 쓴다.

| 결과 | 쓰는 문구 |
|---|---|
| 정적 분석 0건 | 사용한 규칙이 아는 패턴이 코드에 없다. 논리 오류·규칙 밖 패턴은 모른다 |
| 의존성 감사 0건 | 검사 시점에 공개 취약점 DB에 오른 문제가 없다. 미공개 취약점은 모른다 |
| 새니타이저 0건 | 테스트가 실제로 실행한 경로 중 새니타이저로 컴파일한 코드에서 탐지되지 않았다. 미리 빌드된 바이너리·시스템 프레임워크 내부·미실행 경로·누수는 범위 밖이다 |
| 접근성 감사 0건 | 도구가 읽을 수 있는 화면 요소에서 실패가 없었다. 실제 보조 기술 사용감은 모른다 |
| 퍼징(fuzz 테스트) 무크래시 | 생성기가 만든 N건에서 크래시가 없었다 |
| 플랫폼 간 비교(패리티) 일치 | 두 구현이 같은 결과를 냈다. 둘이 같은 방식으로 틀린 경우는 드러나지 않는다 |

같은 질문에 원리가 다른 도구를 겹쳐 쓴다. 보안이면 코드 모양(정적 분석)·공개 취약점(의존성 감사)·실제 실행(공격 입력)·메모리(새니타이저)를 각각 다른 도구로 본다.

## 판정 기준 출처 규칙

- 외부 기준이 둘 이상이면(예: 같은 지표에 엄격한 기준과 느슨한 기준) 어느 쪽을 썼는지와 다른 쪽 값을 함께 적는다.
- 백분위 선택(P90·P95·P99)은 외부 기준이 아니라 프로젝트 선택이다. 판정에 쓴 백분위 밖의 긴 꼬리도 함께 싣는다.
- 주사율에서 계산한 프레임 예산(1,000 ÷ Hz)은 기기가 적응형 주사율이면 근사다.
- 메모리는 절대 상한 대신 추세로 본다. 끝난 뒤에도 계속 늘면 누수 징후, 늘었다가 유지되면 캐시 가능성. 누수 계측을 안 했으면 "반복 시 누적 여부 미확인"으로 적는다.
- 기준을 두지 않은 지표(실행 시간·크기 등)는 값과 구성만 기록하고 판정표에서 뺀다.

## 반복 횟수 기본값

| 측정 | 기본 반복 | 근거 |
|---|---:|---|
| 함수 단위 마이크로 벤치마크(실기기 Release) | 10회 | 예열 뒤 분포 안정. 플랫폼 도구 기본값이 더 크면 그 값(예: 50회) |
| 화면 시나리오 트레이스(스크롤·스트리밍·실행) | 3회 이상, 빌드 비교는 6회 | 녹화·자동화 비용. 3회는 범위 신뢰도 낮음 |
| 극단 입력 시간 | 3회 중앙값 | 같은 입력도 수 % 흔들림 |
| 앱 실행 시간 | 5회 | 콜드·웜 구분해 기록 |

## 결론의 신뢰도 표기

- **확인**: 스크립트로 재실행해 같은 판정이 나왔다.
- **잠정**: 1회 측정, 기기 1대, 또는 측정 구간·시작 위상을 통제하지 않았다. 이유를 함께 적는다.
- **가능성 높음(likely)**: 트레이스 관찰에서 추론한 규칙이고 공개 문서로 확정되지 않았다.
- **미확인**: 환경을 확보하지 못해 실행하지 않았다. 코드 검토나 일부 실행 성공을 이 범위까지 확대하지 않는다.
