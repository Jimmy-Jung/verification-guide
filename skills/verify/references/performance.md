## 측정 원칙

- 절대 성능은 **실기기 Release** 값만 인용한다. 시뮬레이터·에뮬레이터·Debug 값은 같은 조건끼리의 상대 비교와 회귀 게이트에만 쓴다.
- 한 번 잰 값으로 결론 내지 않는다. 반복 횟수와 중앙값·범위를 함께 적는다(principles.md).
- 측정만을 위한 코드를 넣지 않는다. 제품에 원래 있는 가벼운 구간 표시(os_signpost·Trace 섹션)를 측정 구간(window) 지정과 교차 확인에 쓴다.
- 앱 조작은 UI 자동화가 맡고 프로파일러는 밖에서 관찰한다. 단 UI 자동화가 켜는 접근성 모드 자체가 비용이므로, **자동화 없이 자동 재생하는 시나리오**를 따로 둔다.
- 측정마다 기기·OS·빌드 구성·기기 상태(충전·열·저전력)·커밋 SHA·앱/dSYM UUID를 결과와 함께 자동으로 남긴다.
- 도구가 기록한 상태 플래그(예: `cpuLocked=true`)는 실제로 고정한 사실이 아니라 라이브러리 판정값일 수 있다. 별도 실행 기록이 없으면 그렇게 적는다.
- 열 상태가 높은 상태에서 잰 값은 참고값으로 분리한다.

## 지표와 사용자 체감의 대응

지표 하나는 사용자가 겪는 현상 하나에 대응하게 고른다. 보고서에 이 표를 그대로 둔다.

| 지표 | 사용자가 겪는 현상 | 측정 방법 | 판정 기준(출처) |
|---|---|---|---|
| 처리 지연(입력 크기별) | 긴 입력을 표시할 준비까지 걸리는 시간 | 함수 단위 벤치마크, 크기 4단계 이상 | 회귀 방지 기준(시뮬레이터 Debug) + 실기기 값 기록 |
| 화면 끊김(iOS 끊김 시간 비율, ms/s) | 스크롤·갱신 중 툭툭 끊김 | 프로파일러 hitch 계측 | 외부 기준: 플랫폼 제작사 안내 구간 |
| 프레임 시간 백분위(Android) | 같은 현상 | 프레임 타이밍 도구 | 외부 기준: 주사율 프레임 예산(근사) + 프로젝트가 고른 백분위 |
| 메모리 | 오래 쓰면 무거워짐·종료 | 프로세스 footprint 시계열 | 추세: 끝난 뒤 계속 늘지 않음 |
| 앱 실행 시간 | 첫 화면까지 걸리는 시간 | 실행 시간 측정 도구, 콜드·웜 구분 | 기준 없음, 기록만 |
| 앱 크기 | 다운로드·설치 용량 | 씨닝 보고서·패키지 크기, 선택 모듈 조합별 | 기준 없음, 구성 기록 |

## 판정 기준의 출처

- 외부 기준을 먼저 찾고 어느 문서의 어느 기준인지 적는다. 같은 지표에 기준이 둘이면(예: 기술 발표의 엄격한 기준 vs 모니터링 지표의 느슨한 기준) 사용한 쪽과 다른 쪽 값을 함께 적는다.
- 프레임 예산 = 1,000 ÷ 주사율. 적응형 주사율 기기에서는 근사라고 적는다.
- 백분위 선택은 프로젝트 선택이다. 판정에 쓴 백분위 밖의 꼬리(P95·P99)도 싣는다.
- 공식 문서가 끊김과 직접 연결하는 지표(예: 마감 초과 시간)가 따로 있으면 그 값도 함께 싣고, 판정에 쓴 지표가 근사임을 밝힌다.
- 프로젝트가 정한 CI 게이트 값(처리 300 ms 등)은 "체감 기준"이 아니라 "회귀 방지 기준"으로 부른다.

## 도구 교차 확인

핵심 구간 하나를 원리가 다른 도구 2~3개로 잰다: 표본 추출(Time Profiler), 구간 기록(signpost), 반복 시계 측정(XCTest Clock·Microbenchmark). 1% 안에서 맞으면 한 도구의 버릇이 아니다. 계획에 "시나리오 × 도구 2종"을 넣었다면 실제로 교차 확인한 지표와 하지 않은 지표를 보고서에 구분한다. 교차 확인하지 않은 지표에서 보정이 나온다.

## 측정 함정 7종과 대응

실제 보고서를 낸 다음 날 후속 점검에서 드러난 것들이다. 측정 전에 전부 점검한다.

| # | 함정 | 증상 | 대응 |
|---|---|---|---|
| 1 | **고정 측정 구간** | "탭 + 10초"로 잡은 구간에서 작업이 7초에 끝나면 유휴 시간이 분모에 들어가 비율이 희석(약 1.35배)되고, 느린 기기에서는 뒷부분이 잘린다 | 앱이 기록한 구간(signpost 시작~끝)을 측정 구간으로 쓴다. 양 끝 여유는 상수로 두고 명시한다 |
| 2 | **상대 sleep 일정** | 청크 간격을 "처리 후 N ms 쉬기"로 주면 느린 빌드일수록 실제 전송 속도가 낮아져 부하가 줄어든다 | 절대 시각 기준 일정으로 보낸다. 빌드 속도와 상관없이 부하가 같다 |
| 3 | **UI 자동화의 접근성 모드** | UI 테스트가 켠 접근성 트리 유지가 메인 스레드의 두 자릿수 %를 쓴다. 보조 기술을 안 쓰는 사용자에게는 없는 비용 | 자동 재생(접근성 꺼짐) 시나리오를 추가하고 두 시나리오 값을 함께 낸다. "접근성 호출 비용"을 과대 집계하지 않는다 |
| 4 | **데모 화면 비용 혼입** | 데모의 상태 카운터·하단 스크롤이 메인 스레드를 상당 부분 써서 라이브러리 비용이 가려지거나 부풀려진다 | 데모 변경을 분리해 되돌린 빌드로 재측정한다. 긴 테스트 입력을 추가한다 |
| 5 | **반복 합산 백분위** | 반복 5회의 프레임을 합쳐 백분위를 내면 이상 반복 한 번이 P90을 끌어올린다 | 반복별 트레이스를 열어 분포를 확인한다. 합산 P90임을 명시한다 |
| 6 | **hitch 수의 회차 변동** | 같은 빌드·작업량에서 hitch 수가 한 자릿수에서 80건대까지 갈린다. 청크 일정이 vsync 정수배라 시작 위상이 회차 내내 고정되고, 계측기는 늦은 프레임 중 다른 프레임이 표시된 경우만 hitch로 센다(목격자 규칙) | 끊김 시간 비율(hitch ms/s) 하나로 빌드를 비교하지 않는다. 메인 스레드 점유 시간(busy ms/s)과 지연 초과 시간(late excess ms/s: `round(수명/vsync) > 2`인 앱 프레임의 `수명 − 2×vsync` 합)을 함께 본다. 시작을 vsync에 맞추고 시드로 offset을 주되, 실측 시작 위상은 따로 기록한다 |
| 7 | **요약 도구의 inclusive 시간** | 요약 도구(xcprof 등)가 낸 inclusive 시간이 측정 구간 길이에 가깝다 | 시간이 아니라 추정치로 읽는다. 시간 판단은 Time Profiler 표본 수나 구간 표시 합으로 한다(tools.md) |

## 빌드 비교(재측정) 설계

- **같은 날 번갈아.** 두 빌드를 같은 날 같은 기기에서 6회씩, 회차마다 순서를 바꿔(라틴 방진) 잰다. 날짜가 다르면 기기 상태·OS 변화가 섞인다.
- **같은 회차 같은 시드.** 예정 offset을 맞추고 회차별 짝 차이를 구한다. 실측 시작 위상은 보정하지 않았음을 적는다.
- **관측 판정과 인과 효과를 나눈다.** 기준 비교는 관측 중앙값으로, "개선 효과"는 짝 차이가 몇 회 줄었는지로 요약하되 시작 위상을 보정하지 않았으면 인과로 단정하지 않는다.
- **저사양 기기 포함.** 고성능 기기 한 대로는 놓치는 회귀가 있다. 개선이 고성능에서 통과해도 저사양에서 나빠질 수 있다.
- **원인 좁히기.** 개선 단계를 하나씩 되돌린 빌드를 같은 방식으로 잰다. 코어 배치 변화(고성능 코어 비율)처럼 공개 규칙이 없는 설명은 "가능성 높음"으로 둔다.
- **교훈.** 메인 스레드 평균 작업량이 줄었다고 끊김이 줄었다고 판단하지 않는다. 프레임 단위 지표로, 저사양 기기를 포함해 확인한다.

## 측정 전 점검표

```
측정 전 점검:
- [ ] 실기기 Release 빌드, 기기 상태(충전·열·저전력) 기록
- [ ] 측정 구간 = 앱 구간 표시(signpost) (고정 시간 구간 아님)
- [ ] 부하 일정 = 절대 시각 기준
- [ ] UI 자동화 켜짐/꺼짐 시나리오 둘 다
- [ ] 반복 횟수와 순서(번갈아) 결정
- [ ] 결과에 커밋 SHA·앱/dSYM UUID·시드·실측 시작 위상 자동 기록
- [ ] 판정 지표 외에 보조 지표(busy·late excess·P95/P99·마감 초과) 함께 저장
```
