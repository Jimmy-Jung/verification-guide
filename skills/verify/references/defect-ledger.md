# 결함 대장

## ID 체계

머리글자는 영역, 번호는 발견 순서. 한 대장에 전부 넣고 영역으로 구분한다.

| 머리글자 | 영역 | 예 |
|---|---|---|
| F | 제품 결함(코어·파서·로직) | 크래시, 오표시, 시간 폭증 |
| E | 편집기·입력 처리 | 캐럿 이동, undo |
| R | 표시·번들·호환 | 다크 모드, WebView 버전 |
| S | 보안·공급망 | 링크 정책, CI 액션 고정 |
| P | 성능 | 회귀, 재생성 비용 |
| T | 테스트·측정 쪽 보정 | 기한 완화, 재측정 규칙, CI 환경 |
| M | 메모리 안전 | 새니타이저 발견 |
| D | 상위 라이브러리 차이·승인 예외 | 명세 해석 차이(기록만) |

테스트 쪽 보정(T)을 같은 대장에 두는 이유: 숨기면 결과가 좋아진 이유가 코드 수정인지 테스트 완화인지 구분할 수 없다.

## 표 열(7열)

`templates/defect-ledger.csv` 열 순서:

| 열 | 내용 |
|---|---|
| id | `F-01` |
| title | 한 줄 증상 |
| found_by | 발견 경로(퍼징 플랫폼 간 비교 · 극단 입력 · 최소 OS 실행 · 렌더 스냅샷 · 접근성 감사 · 실기기 재측정 · 새니타이저 · CI 첫 실행 · 사전 알려짐) |
| impact | 사용자 영향(크래시 · 글자 손실 · 오표시 · 지연 · 없음) |
| fix | 수정 커밋 또는 "기록만"과 이유 |
| regression | 회귀 테스트 입력 경로 또는 테스트 이름. 기록만이면 비움 |
| status | 수정 · 기록 · 보류(조건) |

## 발견 경로를 적는 이유

각 검증 방법이 실제로 결함을 찾았는지의 근거가 된다. 보고서에 "방법 → 찾은 결함" 표를 만든다. 검증 전부터 알려진 결함은 표에서 빼고 "사전 알려짐"으로 표시한다.

## 수정 후 재실행과 출력 동일성

- 수정 전에 실패하던 테스트가 수정 후 통과하는지 확인한다.
- 출력을 바꾸면 안 되는 수정(성능 최적화, 스택 프레임 분리)은 퍼징(fuzz 테스트) 전체와 공용 입력 모음(코퍼스) 전체의 정규화 결과가 수정 전과 **바이트 단위로 같은지** 비교한다.
- 전체 검증을 다시 돌려 다른 곳이 깨지지 않았는지 확인한다.

## 상위 라이브러리 차이를 기록만 하는 이유

두 구현이 쓰는 오픈소스 라이브러리의 명세 해석 차이는 고치지 않고 D로 기록한다. 단 글자 보존이 깨지는 경우(문자 참조를 U+FFFD로 대체 등)는 "같은 글자를 보존한다"고 말하지 않는다. 퍼징 잔여 차이가 전부 D 항목 안에 들어가는지 스크립트로 확인하고, 대응되지 않는 차이 0건을 판정 조건으로 둔다.

## 보고서 요약 문구

"결함 N건"에는 테스트 보정·상위 차이·결함이 아니라고 확인한 항목이 들어 있음을 적고, 영향이 컸던 항목(크래시·시간 폭증·오표시)을 따로 센다. 고친 결함에는 모두 재현 입력이나 회귀 테스트가 있는지 적는다.
