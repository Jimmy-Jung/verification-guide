# Q1 오류 — 정확성·견고성 검증 방법

## 차례
- 방법 선택 지도
- 공용 입력 모음(코퍼스)
- 차등 테스트와 플랫폼 간 비교(패리티)
- 속성 기반 퍼징(fuzz 테스트)
- 극단 입력
- 렌더 수준 검사
- 최소·최신 OS 실행
- 결함을 고칠지 기록만 할지

## 방법 선택 지도

| 상황 | 방법 | 이유 |
|---|---|---|
| 입력마다 정답을 사람이 적기 어렵다 | 차등 테스트 + 속성 기반 퍼징 | 기댓값 없이 "두 구현의 차이"와 "항상 지켜야 할 성질"로 판정한다 |
| 공개 명세가 있다 | 명세 예제를 공용 입력 모음에 넣기 | 경계 사례의 다양성을 외부에서 빌린다 |
| 스택 넘침·O(n²)이 의심된다 | 극단 입력 | 퍼징 변형은 국소적이라 수백 단계 중첩·수만 번 반복을 만들지 못한다 |
| 파서는 맞는데 화면이 틀릴 수 있다 | 스트리밍 동등성·렌더 스냅샷·접근성 감사 | 화면 경로는 코드가 다르다 |
| 선언한 최소 OS가 있다 | 최소·최신 OS 실행 | 시스템 구성 요소(URL 파서·WebView)가 버전마다 다르다 |

## 공용 입력 모음(코퍼스)

계약은 [templates/fixture-contract.md](../templates/fixture-contract.md)를 쓴다. 핵심 규칙:

- **범주**: 공개 명세 예제(크래시·시간만 검사, 플랫폼 간 비교 입력), 도메인 경계(수식·표 등), 유니코드(결합 문자·RTL·ZWJ·BOM·CRLF·zero-width), 스트리밍 중간 상태(닫히지 않은 구조), 보안 입력(링크 스킴·HTML), 극단 입력, 회귀(결함별 최소 재현).
- **정본 한 곳**: 한 저장소에 정본을 두고 다른 저장소는 `fixtures_manifest.py --check`로 SHA-256을 대조한 뒤 쓴다. 사본을 각자 고치면 결과 차이가 코드 때문인지 입력 때문인지 구분할 수 없다. 해시 대조는 양쪽 CI에서 커밋마다 돈다.
- **기대 조건**: 명세 예제를 뺀 범주는 입력마다 기대 결과 또는 기대 조건(사이드카)을 둔다.
- **러너 출력**: 블록 종류·순서·글자·범위·링크·크기만 남긴 플랫폼 중립 정규화 결과(JSON). 픽셀이 아니라 구조를 비교한다.

## 차등 테스트와 플랫폼 간 비교(패리티)

같은 입력을 독립된 두 구현에 넣고 정규화 결과를 비교한다. 독립성이 높은 부분(다른 상위 파서)에서 가장 잘 드러나고, 같은 설계를 두 언어로 옮긴 계층은 함께 틀릴 수 있다.

절차:
1. 양쪽 러너가 `<out>/<platform>/<name>.json`을 낸다.
2. 비교 스크립트가 **일치 / 승인 예외 / 미해결 차이**로 나눈다. 미해결이 있으면 종료 코드 1.
3. 미해결은 결함 후보다. 명세·지원 계약과 대조해 "고칠 결함", "승인 예외(이유 기록)", "상위 파서 차이(기록만)" 중 하나로 판정한다.
4. 승인 예외 목록(`parity-exceptions.json` 등)은 ID와 이유를 가진다.

한계를 보고서에 적는다:
- 두 구현이 같은 방식으로 틀리면 드러나지 않는다. 회귀 테스트 입력과 성질 검사로 일부 보완하고, 독립된 정답 판정 기준이 없음을 명시한다.
- 비교기의 정규화가 의미를 잃을 수 있다(예: URL 퍼센트 디코딩이 `/a%2Fb`와 `/a/b`를 같게 봄). 비교기의 한계도 적는다.
- 양쪽 출력의 합집합만 비교하면 함께 빠진 입력은 못 찾는다. 예상 ID 집합과 건수를 별도로 확인한다.

## 속성 기반 퍼징(fuzz 테스트)

무작위 입력의 정답은 모르므로 **입력이 무엇이든 지켜야 할 성질**을 검사한다.

- **성질 예**: 무크래시, 입력당 시간 상한, 보호→복원 뒤 바이트 동일, 범위·인코딩 경계 준수, 상한 초과 진단, 모든 prefix 무크래시, 조각 누적 최종 결과 == 전체 처리 결과, 편집 N회 → undo N회 == 원본.
- **변형**: 기호 삽입(도메인 기호 + 유니코드 특수 문자 풀), 한 글자 삭제, 짧은 구간 복제, 구분자 하나 삭제, 줄바꿈 변형, 앞부분만 남기기. 횟수보다 **변형 종류의 다양성과 실패 입력 최소화**가 효과를 좌우한다.
- **시드 고정**: SplitMix64 등 결정적 생성기. 시드와 반복 번호만으로 같은 입력을 재현한다. 두 플랫폼이 같은 알고리즘·시드로 바이트 단위까지 같은 입력열을 만들면 퍼징 결과도 입력별로 플랫폼 간 비교가 된다.
- **규모**: CI 1만 회(커밋마다 감당할 시간), 릴리스 전 수동 10만 회. 실측 시간으로 조정한다. 10만 회에서만 나온 결함이 있을 수 있다.
- **실패 처리**: 테스트가 입력을 자동 최소화해 `fixtures/regressions/<seed>-<n>`에 저장한다.
- **잔여 차이 분류**: 플랫폼 간 비교 일치율만으로는 남은 차이가 결함인지 모른다. 잔여 차이를 원인별로 분류하는 스크립트를 두고, **분류되지 않은 차이 0건**을 판정 조건으로 삼는다. 분류 과정에서 결함이 추가로 나온다.
- **시간 상한의 흔들림**: 공유 CI 러너의 일시 지연으로 상한을 넘으면 같은 입력을 3회 다시 재서 가장 빠른 값으로 판정한다. 입력 자체가 느리면 세 번 다 넘어 그대로 실패한다. 이 완화는 결함 대장(T)에 기록한다.

## 극단 입력

정상 사용에서는 드물지만 구조가 극단적인 입력(pathological input). 생성 규칙으로 만든다(목록 수백 단계 중첩, 기호 수만 개, 수백 KB 한 줄 등). 자원 고갈 위협(Q3)을 대신하는 입력이기도 하다.

측정 조건에 이유를 붙인다:
- **Release 빌드**: Debug는 시간이 크게 부풀어 보인다(같은 입력이 Debug 12.9초, Release 0.3초였던 사례).
- **실제 실행 스레드와 같은 스택 크기**: 스택 넘침 조건이 그대로 재현되게.
- **3회 중앙값**: 작은 차이는 해석하지 않는다.
- **수정 전후 같은 조건 비교**: 개선뿐 아니라 느려진 입력도 드러나게. 느려진 입력도 보고서에 적는다.

## 렌더 수준 검사

- **스트리밍 동등성**: 조각으로 흘려 그린 최종 결과 == 한 번에 그린 결과. 조각 크기 여러 개(1·7·64·1024…)로. 화면 구조 비교이지 픽셀이 아니다.
- **렌더 스냅샷**: 대표 입력 × 라이트/다크 × 글자 크기. 기준 이미지와 허용 오차 비교. 다크 모드 전용 결함이 여기서 나온다.
- **자동 접근성 감사**: 플랫폼 감사 API. 정해진 규칙만 보고, 보조 기술 실사용 확인을 대신하지 못한다. 그 부분은 "출시 전 사람 확인"으로 남긴다.

## 최소·최신 OS 실행

선언한 최소 OS와 최신 OS에서 핵심 테스트를 돌린다. 시스템 URL 파서·WebView 버전·UI 동작 차이에서 실제 결함이 나온다. CI가 고르는 OS와 로컬에서 돌린 OS가 다르면 CI 첫 실행에서야 드러나므로, 데모·UI 테스트는 두 OS에서 확인한다. 실기기를 확보하지 못한 OS는 "시뮬레이터만"으로 적는다.

## 결함을 고칠지 기록만 할지

두 기준으로 정한다. ① 원인이 우리 코드인지 상위 라이브러리인지 ② 사용자에게 글자 손실·가림·크래시가 보이는지. 상위 라이브러리 원인이라도 사용자에게 보이면 우리 쪽에서 보정해 고친다. 명세 해석 차이로 구조만 다르면 기록한다(defect-ledger.md의 D). 상위 저장소가 바뀌면 다시 확인한다.
