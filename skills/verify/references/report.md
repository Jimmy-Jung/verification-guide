# 계획 문서와 검증 보고서

## 차례
- 계획 문서 목차
- 보고서 목차
- 수치 파이프라인
- 부록 구성
- 표기 규칙
- 독자별 파생본
- 공개 사본 규칙
- 방법 해설·도구 문서(선택)

## 계획 문서 목차

`templates/plan.md`. 0 배경·목표·원칙 → 1 현재 상태(실측 표, 가용 환경 표) → 2 요구사항(2-1 보고서가 답할 질문, 2-2 프로젝트 보강 FR, 2-3 보고서 RR, 2-4 제약) → 3 검증 설계(의사코드) → 4 작업 단계 → 5 보고서 목차 초안 → 6 확정된 결정 → 7 리스크 → 8 도구 설명 → 9 진행 체크리스트.

사용자 결정이 필요한 항목은 한 번에 묻고 §6에 날짜와 함께 고정한다(양식·결함 수정 범위·커밋/태그·도구 설치·기기·회사명 언급·퍼징 규모).

## 보고서 목차

`templates/report.md`. 요약(서술형 초록) → 1 배경과 범위(1.1 검증 질문, 1.2 대상·범위 밖) → 2 검증 방법(2.1 파이프라인, 2.2 테스트 계층, 2.3 도구, 2.4 실행 환경) → 3 테스트 보강(규모, 공용 입력 모음(코퍼스), 퍼징(fuzz 테스트), 플랫폼 간 비교(패리티)) → 4 Q1 결과 → 5 Q2 결과(측정 구성 → 지표별 → 교차 확인 → 판정표) → 6 Q3 결과(위협 모델 → 정적·의존성 → 동적 → 메모리) → 7 Q4 결과(커버리지, 복잡도, CI) → 8 남은 조건과 확인하지 않은 범위(논문의 타당성 위협) → 9 결론(조건부 권고, 남은 리스크 표) → 참고문헌 → 부록 A 결함 대장, B 재현 명령, C 원시 데이터 위치.

판정표(5.8 등)는 플랫폼 값을 각자의 기준 옆에만 둔다. 요약은 결론·조건부 권고·남은 리스크를 서술형 3~5문장으로 쓰고, 리스크 표는 9절에 둔다.

## 수치 파이프라인

```
원시 결과(xcresult · trace · 벤치 JSON · 정적 분석 JSON · 커버리지 · 결함 대장)
  → scripts/report/collect.py   → data/*.csv          # 단일 출처. 없는 원시 파일은 건너뛰고 stderr에 적는다
  → scripts/report/charts.py    → assets/charts/*.png # CSV만 읽는다
  → 도식 빌드 스크립트           → assets/diagrams/*.svg
  → report.md                                          # 본문 표는 CSV에서 옮기고 출처 명시
  → 저장소 사본 (경로 치환, 공개 사본 규칙)
  → docx · pptx · pdf (문서 스킬)
  → 검수: 본문 수치 ↔ CSV 대조, 링크·이미지 검사, 렌더 확인
```

- 재현 가능성 확인: 같은 원시 결과로 두 스크립트를 다시 돌려 CSV는 바이트 단위, 그래프는 픽셀 단위로 같은지 확인하고 그 사실을 2.1절에 적는다.
- 자동 생성 부분과 수동 전사 부분을 구분해 적는다. 스크립트 상수로 적은 값(보강 전 테스트 수 등)도 밝힌다.
- 원시 결과가 작성자 기기에만 있으면 부록 C에 그 사실과 공유 방법을 적는다.

## 부록 구성

- **A 결함 대장**: `defect-ledger.md` 7열. 영역별 소계.
- **B 재현 명령**: 공용 입력 모음 출력·플랫폼 간 비교·퍼징(시드·규모)·CI 게이트·정적 분석·측정 스크립트 명령. 환경 변수 전달 방식(예: `TEST_RUNNER_` 접두사)까지.
- **C 원시 데이터 위치**: 저장소 안/밖 구분, 작업 폴더 키.

## 표기 규칙

- 기기: 모델·칩·출시 시기·OS 버전. 예: "iPad Pro 11형(M5, 2025년 10월 출시, iPadOS 26.6.2)". "최신 세대" 같은 모호 표현 금지.
- 수치 옆: 환경(기기·OS·빌드 구성)·반복·날짜·커밋. 추정값은 "추정".
- 요약은 서술형 초록 3~5문장(무엇을·왜·핵심 판단 기준·한계). 목록을 쓰지 않는다.
- 캡션(명사형, 문서마다 1부터): 표는 바로 위 `*표 N. …*`, 그림은 바로 아래 `*그림 N. …*`. 그림 안에 제목을 넣지 않는다. 본문에서 "표 N"·"그림 N"으로 가리키고 그림의 핵심을 문장으로도 쓴다.
- 참고문헌은 번호식 `[1] 저자·기관, "제목", 출처, URL`. 본문에서 [1]로 인용한다.
- 출력 예시 블록 위에는 출력 형식을 보여 주는 예라는 문장을 둔다. 값을 지어냈으면 "가상"이라고, 실제 측정값이면 그 출처를 밝힌다. 출처를 모르면 단정하지 않는다.
- 절 제목은 명사형. 질문형 소제목은 관리자용 파생본의 우려 절에만.
- "N절"은 자기 문서, "보고서 N절"은 보고서를 가리킨다고 1절에 정의한다.
- 측정 방법을 나중에 고쳤으면 첫 판 수치와 재측정 수치를 구분하고 보정 방향을 적는다.

## 독자별 파생본

- **관리자용 도입 검토 보고서**: 독자(팀장·실장·임원), 요약은 서술형 초록, 4장은 우려 네 가지를 질문형 소제목으로, 대안 비교는 "실측 없는 일반론"으로 명시. 인력 체제·결정 요청 문구는 사용자 결정에 따른다.
- **발표(pptx)**: 18–22장, 결론·조건·리스크 먼저.
- **논문형(docx·pdf)**: 국문 초록·영문 Abstract·서론·배경·설계·방법·결과·논의(타당성 위협)·결론·참고문헌·부록. 1단, 번호식 참고문헌.
- 파생본의 수치는 모두 같은 CSV에서 나온다.

## 공개 사본 규칙

회사명·개인 이름(저자 표기 제외)·이메일·로컬 절대 경로·볼륨 이름·내부 장치 식별자를 제거한다. 공개 저장소 이름과 실기기 모델명은 둔다.

## 방법 해설·도구 문서(선택)

보고서와 별도로 "무엇을, 어떻게, 왜 그렇게 검증했나" 해설과 도구별 카드(`templates/tool-card.md`)를 두면 리뷰 질문("AI가 쓴 테스트로 AI 코드를 검증하면 의미 있나", "커버리지 92%면 버그 없나", "기기 두 대로 충분한가")에 바로 답할 수 있다. 예상 질문과 답 절을 해설 끝에 둔다.
