# 용어 풀이 — 검증 문서에서 자주 만나는 말

이 문서는 검증 가이드 문서를 읽다가 멈추게 되는 용어를 한두 문장으로 풀어 둔 목록입니다. 한글 용어는 가나다순으로, 영문 약어나 도구 이름으로 시작하는 용어는 끝에 알파벳순으로 모았습니다. 항목마다 자세한 설명이 있는 문서도 함께 적었습니다.

## 한글 용어

### 결함 대장

검증하면서 찾은 결함을 번호·발견 경로·수정 내용·회귀 테스트와 함께 한 표에 모은 목록입니다. 고친 결함뿐 아니라 기록만 하고 고치지 않은 상위 라이브러리 차이와 테스트 쪽 보정도 같은 표에 남겨, 결과가 좋아진 이유를 나중에 가릴 수 있게 합니다.

관련 문서: [기록과 보고의 결함 대장](06-records-and-reports.md#3-결함-대장)

### 공용 입력 모음

여러 플랫폼·저장소가 함께 쓰는 테스트 입력 묶음으로, 코퍼스(corpus)라고도 부릅니다. 한 저장소에 정본을 두고, 다른 저장소는 SHA-256 해시를 대조해 사본이 정본과 같은지 확인한 뒤 씁니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 구간 표시(signpost)

앱 코드가 "여기서 시작, 여기서 끝"을 기록하는 가벼운 표시입니다. 프로파일러가 이 표시를 읽으므로 지표를 실제 작업 구간에서만 계산할 수 있습니다. iOS에서는 `os_signpost`로 남깁니다.

관련 문서: [측정 함정](03-performance.md) · [Instruments와 xctrace](tools/ios-performance.md#3-instruments와-xctrace--앱이-도는-동안-cpu-표본프레임-hitch메모리구간을-한-타임라인trace에-기록하고-분석하는-도구)

### 극단 입력

정상 사용에서는 드물지만 구조가 극단적인 입력으로, 영어로는 pathological input이라고 합니다. 수백 단계로 중첩되거나 같은 기호가 수만 개 반복되는 입력처럼 처리 시간이나 메모리를 크게 늘릴 수 있는 경우를 가리킵니다.

관련 문서: [정확성·견고성 검증](02-correctness.md) · [보안 검증](04-security.md)

### 끊김 시간 비율

1초 동안 늦게 표시된 시간의 합을 ms/s 단위로 나타낸 값입니다. Instruments(Xcode에 딸린 성능 분석 도구)에서는 hitch time ratio라고 부릅니다. 측정 구간 안의 hitch 시간을 모두 더해 구간 길이(초)로 나눠 구합니다.

예: Apple Tech Talk 10855는 5 ms/s 미만을 좋음, 5~10 ms/s를 조사 필요, 10 ms/s 초과를 나쁨으로 봅니다.

관련 문서: [성능 검증](03-performance.md) · [Instruments와 xctrace](tools/ios-performance.md#3-instruments와-xctrace--앱이-도는-동안-cpu-표본프레임-hitch메모리구간을-한-타임라인trace에-기록하고-분석하는-도구)

### 라틴 방진

빌드처럼 여러 대상을 비교할 때 각 대상이 순서의 모든 자리에 고르게 오도록 회차마다 실행 순서를 돌리는 실험 배치입니다(Latin square). 한 빌드를 연속으로 다 재면 시간에 따른 기기 온도 변화가 빌드 차이로 둔갑하므로, 두 빌드를 번갈아 재면서 순서를 바꿉니다.

예: 1회차는 A → B, 2회차는 B → A 순서로 잽니다.

관련 문서: [성능 검증](03-performance.md)

### 메인 스레드 점유 시간(busy ms/s)

측정 구간에서 메인 스레드가 1초 동안 일한 시간입니다. 시작 위상과 상관없이 회차 간 변동이 작아서, hitch 수가 크게 갈릴 때 작업량이 실제로 달라졌는지 가리는 데 씁니다.

관련 문서: [측정 함정](03-performance.md)

### 목격자 규칙

늦은 앱 프레임이 화면에 머무는 동안 다른 프레임이 표시된 경우에만 계측기가 그 프레임을 hitch로 세는 것으로 보이는 규칙입니다. 트레이스 관찰에서 추론했고 제작사 문서로 확정되지 않았으므로 신뢰도는 "가능성 높음"입니다.

관련 문서: [측정 함정](03-performance.md)

### 백분위(P90)

값을 크기순으로 놓았을 때 90%가 이 값 이하가 되는 지점입니다. 중앙값은 P50에 해당하고, P95·P99는 더 드문 느린 값을 봅니다. 어느 백분위를 판정에 쓸지는 외부 기준이 아니라 프로젝트가 고릅니다.

관련 문서: [검증 원칙과 해석 원칙](01-principles.md) · [측정 함정](03-performance.md)

### 새니타이저

실행 중 메모리 오류(AddressSanitizer, ASan)와 데이터 경합(ThreadSanitizer, TSan)을 잡도록 빌드에 검사 코드를 넣는 컴파일러 기능입니다. 테스트가 실제로 실행한 경로만 검사하므로 0건은 커버리지와 함께 읽습니다. HTML에서 위험한 부분을 걷어 내는 HTML 새니타이저(DOMPurify 등)와는 다른 도구입니다.

관련 문서: [보안 검증](04-security.md) · [AddressSanitizer](tools/ios-performance.md#5-addresssanitizer--범위-밖-접근해제-후-사용-같은-메모리-손상을-테스트가-도는-동안-잡아내는-컴파일러-기능) · [ThreadSanitizer](tools/ios-performance.md#6-threadsanitizer--동기화-없이-두-스레드가-같은-메모리에-접근하는-데이터-경합을-테스트가-도는-동안-찾는-컴파일러-기능)

### 속성 기반 테스트

입력이 무엇이든 항상 지켜야 할 성질을 검사하는 방식입니다(property-based testing). 무작위 입력에는 정답을 미리 정해 둘 수 없으므로 "크래시가 없다", "조각을 누적한 결과가 한 번에 처리한 결과와 같다"처럼 정답 없이 확인할 수 있는 성질만 검사합니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 승인 예외

차이를 알고도 이유를 기록하고 허용한 항목입니다. 차등 테스트의 결과는 일치·승인 예외·미해결 차이로 나뉘며, 승인 예외는 이유를 남겨 두므로 분류되지 않은 차이로 세지 않습니다.

관련 문서: [정확성·견고성 검증](02-correctness.md) · [기록과 보고의 결함 대장](06-records-and-reports.md#3-결함-대장)

### 시드

난수 생성의 시작값(seed)입니다. 시드가 같으면 같은 입력열이 나오므로, 퍼징에서 실패한 입력을 시드만으로 다시 만들 수 있습니다. 다만 같은 시드가 스레드 깨어남 지연 같은 실행 환경까지 같게 만들지는 않습니다.

관련 문서: [정확성·견고성 검증](02-correctness.md) · [측정 함정](03-performance.md)

### 시작 위상

작업 시작 시각이 vsync 주기의 어느 지점에 걸리는지를 말합니다. 청크(스트림으로 보내는 조각) 간격이 vsync 간격의 정수배이면 시작 위상이 한 회차 내내 고정되어, 같은 빌드라도 회차마다 hitch 수가 크게 갈릴 수 있습니다.

관련 문서: [측정 함정](03-performance.md)

### 실기기

시뮬레이터·에뮬레이터가 아닌 실제 기기입니다. 사용자 체감을 말하는 성능 값은 실기기의 Release 빌드에서 잽니다.

관련 문서: [검증 원칙과 해석 원칙](01-principles.md) · [성능 검증](03-performance.md)

### 외부 기준

플랫폼 제작사·공식 문서가 정한 판정 기준입니다. 어느 문서의 어느 기준인지 함께 적고, 같은 지표에 기준이 둘 이상이면 어느 쪽을 썼는지 밝힙니다.

예: 끊김 시간 비율에는 Apple Tech Talk의 5·10 ms/s 기준과 Xcode Organizer의 10·25·50 ms/s 기준이 따로 있습니다.

관련 문서: [검증 원칙과 해석 원칙](01-principles.md) · [성능 검증](03-performance.md)

### 위협 모델

무엇을 지키는지, 믿을 수 없는 데이터가 어디로 들어와 무엇을 노리는지 정리한 표·그림입니다. 보안 검증은 위협 모델을 먼저 세우고, 위협마다 공격 입력을 넣어 막히는지 확인하는 순서로 진행합니다.

관련 문서: [보안 검증](04-security.md)

### 의존성 감사

프로젝트가 쓰는 외부 라이브러리와 버전을 공개 취약점 데이터베이스와 대조하는 검사입니다. 0건은 검사 시점에 공개된 취약점이 없다는 뜻이고, 공개되지 않은 취약점은 알 수 없습니다.

관련 문서: [보안 검증](04-security.md) · [osv-scanner](tools/common-security-quality.md#3-osv-scanner--의존성-목록을-공개-취약점-데이터베이스와-대조하는-도구) · [npm audit](tools/common-security-quality.md#4-npm-audit--프로젝트의-npm-의존성에-알려진-취약점이-있는지-묻는-명령)

### 정규화 결과

비교하기 쉽게 같은 형식(JSON)으로 바꾼 결과입니다. 두 구현의 내부 표현이 달라도 블록 종류·순서·글자·범위처럼 비교에 필요한 구조만 남기면 결과끼리 맞춰 볼 수 있습니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 정답 판정 기준

결과가 맞는지 독립적으로 판단해 주는 기준으로, 영어로 오라클(oracle)이라고 합니다. 차등 테스트에는 두 구현이 함께 틀린 경우를 가려 줄 정답 판정 기준이 없다는 한계가 있습니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 정적 분석

코드를 실행하지 않고 소스의 모양을 규칙과 맞춰 위험한 패턴을 찾는 검사입니다. 규칙이 아는 패턴만 찾으므로 0건은 "규칙 밖 패턴과 논리 오류는 모른다"는 말과 함께 읽습니다.

관련 문서: [보안 검증](04-security.md) · [semgrep](tools/common-security-quality.md#2-semgrep--코드를-실행하지-않고-규칙과-맞춰-위험한-모양을-찾는-도구)

### 중앙값·범위

측정값을 크기순으로 놓았을 때의 가운데 값과 최솟값~최댓값입니다. 중앙값은 한 번 튄 값에 끌려가지 않아 보통의 실행을 나타내고, 범위는 가장 나빴던 실행까지 보여 줍니다.

예: 세 번 잰 값이 2, 3, 30이면 중앙값은 3, 범위는 2~30입니다.

관련 문서: [검증 원칙과 해석 원칙](01-principles.md)

### 지연 초과 시간(late excess ms/s)

두 프레임 주기를 넘겨 늦은 프레임들에서, 넘긴 시간만 모두 더해 측정 구간 길이로 나눈 값입니다. 다른 프레임이 표시됐는지와 상관없이 세므로, 목격자 규칙의 영향을 받는 hitch 수를 보완합니다.

관련 문서: [측정 함정](03-performance.md) · [성능 검증](03-performance.md)

### 차등 테스트

같은 입력을 서로 다른 두 구현에 넣고 결과를 비교하는 테스트(differential testing)입니다. 입력마다 정답을 적지 않아도 차이가 난 입력을 단서로 결함을 찾을 수 있지만, 두 구현이 같은 방식으로 틀리면 드러나지 않습니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 측정 구간

지표를 계산하는 시간 범위로, 영어 window를 옮겨 측정 창이라고 부르기도 합니다. 측정 구간을 시계로 고정하면 유휴 시간이 섞이거나 작업이 잘리므로, 구간 표시로 잡은 실제 작업 구간을 씁니다.

관련 문서: [측정 함정](03-performance.md)

### 커버리지

테스트가 실행한 코드 줄(또는 분기)의 비율입니다. 결과가 맞는지 검사했다는 뜻은 아니므로, 테스트가 닿지 않은 곳을 찾는 지표로 씁니다.

관련 문서: [유지보수·자동화 검증](05-maintenance.md) · [xccov](tools/ios-testing.md#5-xccov--xcresult의-코드-커버리지를-타깃파일함수줄-단위로-읽는-xcode-명령행-도구) · [Kover](tools/android-testing.md#5-kover--jvm-단위-테스트가-kotlin-코드의-어느-줄을-실행했는지-재는-커버리지-플러그인) · [JaCoCo](tools/android-testing.md#6-jacoco--에뮬레이터-계측-테스트가-실행한-줄을-재는-커버리지-도구agp-내장)

### 테스트 입력

테스트에 넣는 고정 입력 파일로, 영어로 fixture라고 합니다. 결함을 고친 뒤 남기는 최소 재현 입력도 테스트 입력의 한 종류입니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 트레이스

프로파일러가 앱 실행 중 일어난 일(함수 표본, 프레임 표시 시각, 구간 표시 등)을 시간순으로 기록한 파일입니다. 요약 수치가 이상하면 트레이스를 직접 열어 반복별·프레임별로 확인합니다.

관련 문서: [Instruments와 xctrace](tools/ios-performance.md#3-instruments와-xctrace--앱이-도는-동안-cpu-표본프레임-hitch메모리구간을-한-타임라인trace에-기록하고-분석하는-도구) · [Perfetto](tools/android-performance.md#5-perfetto--android-기기에서-일어난-일을-시간축으로-보고-sql로-묻는-추적-도구) · [측정 함정](03-performance.md)

### 퍼징

입력을 무작위로 바꿔 대량으로 넣고 이상 동작을 찾는 테스트입니다(fuzzing, 퍼즈 테스트). 이 가이드에서는 시드를 고정해 같은 입력열을 다시 만들 수 있게 하고, 실패한 입력은 최소화해 회귀 테스트 입력으로 남깁니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 프레임 예산

한 프레임에 쓸 수 있는 시간으로, 1,000 ÷ 주사율로 계산합니다. 적응형 주사율 기기에서는 근삿값입니다.

예: 120 Hz면 8.33 ms, 60 Hz면 16.67 ms입니다.

관련 문서: [검증 원칙과 해석 원칙](01-principles.md) · [성능 검증](03-performance.md)

### 플랫폼 간 비교

iOS·Android 결과가 같은지 맞춰 보는 일로, 문서에서 패리티(parity)라고도 씁니다. 두 플랫폼 구현을 대상으로 한 차등 테스트이며, 결과는 일치·승인 예외·미해결 차이로 나눕니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### 하네스

측정 대상 앱을 같은 조건으로 실행·조작하고 결과를 모으는 측정용 코드와 스크립트 묶음입니다. 하네스의 일정·측정 구간·집계 방식이 틀리면 측정 대상과 무관한 이유로 값이 움직입니다.

관련 문서: [측정 함정](03-performance.md) · [성능 검증](03-performance.md)

### 화면 갱신 신호(vsync)

디스플레이가 다음 프레임을 받을 준비가 됐다고 알리는 주기 신호입니다. 120 Hz 화면이면 약 8.33 ms마다 오며, 앱 프레임이 이 신호에 맞춰 준비되지 못하면 화면 끊김이 생깁니다.

관련 문서: [측정 함정](03-performance.md) · [Instruments와 xctrace](tools/ios-performance.md#3-instruments와-xctrace--앱이-도는-동안-cpu-표본프레임-hitch메모리구간을-한-타임라인trace에-기록하고-분석하는-도구)

### 화면 끊김(hitch)

프레임이 제때 화면에 나가지 못해 툭 끊겨 보이는 현상입니다. Instruments는 예정보다 늦게 표시된 프레임을 hitch로 세고, 그 시간을 모아 끊김 시간 비율을 냅니다.

관련 문서: [성능 검증](03-performance.md) · [Instruments와 xctrace](tools/ios-performance.md#3-instruments와-xctrace--앱이-도는-동안-cpu-표본프레임-hitch메모리구간을-한-타임라인trace에-기록하고-분석하는-도구)

### 회귀 방지 기준

프로젝트가 정한 값으로, "나빠지면 CI를 실패시키는" 장치입니다. 커버리지 하한이나 처리 시간 상한이 여기에 속하며, 사용자 체감의 근거가 아니라 변화를 감지하는 선으로 읽습니다.

관련 문서: [검증 원칙과 해석 원칙](01-principles.md) · [유지보수·자동화 검증](05-maintenance.md)

### 회귀 테스트 입력

고친 결함이 다시 생기면 걸리도록 남겨 두는 최소 재현 입력입니다. 커밋마다 CI에서 다시 검사합니다.

관련 문서: [정확성·견고성 검증](02-correctness.md) · [기록과 보고의 결함 대장](06-records-and-reports.md#3-결함-대장)

## 영문 용어

### AAR

Android Archive의 줄임말로, Android 라이브러리를 배포하는 패키지 형식입니다. 코드·리소스와 함께 미리 빌드된 네이티브 라이브러리(.so)를 담을 수 있으며, 안에 든 .so에는 새니타이저 검사 코드가 들어가지 않습니다.

관련 문서: [보안 검증](04-security.md)

### BufferQueue

Android에서 앱이 그린 프레임 버퍼를 시스템 화면 합성기로 넘기는 대기열입니다. 버퍼가 밀리면(stuffing) 앱이 빈 버퍼를 받아 오는 `dequeueBuffer` 호출에서 막혀 프레임이 늦어집니다.

관련 문서: [측정 함정](03-performance.md) · [Jetpack Macrobenchmark](tools/android-performance.md#3-jetpack-macrobenchmark--앱을-밖에서-조작하며-실행-시간과-프레임-시간을-재는-라이브러리)

### CI 게이트

커밋·PR마다 자동으로 돌고, 실패하면 병합을 막는(막을 수 있는) 검사입니다. 저장소에 브랜치 보호 규칙이 없으면 검사가 실패해도 병합이 막히지 않으므로 보호 설정을 함께 확인합니다.

관련 문서: [유지보수·자동화 검증](05-maintenance.md)

### CommonMark

CommonMark는 Markdown 해석 규칙을 모호하지 않게 정한 공개 명세이고, GFM(GitHub Flavored Markdown)은 여기에 표·작업 목록·취소선·자동 링크 같은 확장을 더한 GitHub의 명세입니다. 두 구현의 결과가 다를 때 어느 쪽이 맞는지 이 명세의 문장과 예제로 판정합니다.

관련 문서: [정확성·견고성 검증](02-correctness.md)

### CSP

Content Security Policy의 줄임말로, 웹 페이지나 WebView가 어떤 출처의 스크립트·리소스를 불러오고 실행할 수 있는지 제한하는 보안 설정입니다. 악성 입력이 스크립트를 넣더라도 실행되지 않게 막는 방어 가운데 하나입니다.

관련 문서: [보안 검증](04-security.md)

### DOMPurify

HTML에서 스크립트 태그나 이벤트 속성(`onerror` 등)처럼 실행될 수 있는 부분을 걷어 내는 JavaScript 라이브러리입니다. 이런 HTML 정화 도구도 새니타이저라고 부르지만, 컴파일러 기능인 ASan·TSan과는 다른 것입니다.

관련 문서: [보안 검증](04-security.md)

### FFI

Foreign Function Interface의 줄임말로, 한 언어로 쓴 코드가 다른 언어(C·Rust 등)로 만든 함수를 부르는 경계입니다. Swift·Kotlin 같은 메모리 안전 언어의 보장이 이 경계 너머에는 닿지 않으므로, 입력 상한을 주된 방어로 두고, 새니타이저는 보조 확인에 씁니다.

관련 문서: [보안 검증](04-security.md)

### inclusive 시간

프로파일러에서 한 함수가 자기 코드에서 쓴 시간에 그 함수가 부른 하위 함수의 시간까지 더한 값입니다. 일부 요약 도구는 이 값을 "표본 비율 × 측정 구간 길이"로 추정하므로, 측정 구간 길이에 가까운 값이 나오면 실제 시간이 아닌 추정치일 수 있다고 의심합니다.

관련 문서: [측정 함정](03-performance.md) · [xcprof](tools/ios-performance.md#4-xcprof--xctrace로-녹화한-cpu-profiler-트레이스를-함수별-비중과-메인-스레드-요약으로-풀어-주는-서드파티-도구)

### JNI

Java Native Interface의 줄임말로, Android에서 Kotlin·Java 코드가 C·C++·Rust 같은 네이티브 코드를 부를 때 쓰는 FFI입니다. iOS에서 돌린 새니타이저는 Android의 JNI 경로를 검사하지 못하므로, Android에서 따로 실행해야 합니다.

관련 문서: [보안 검증](04-security.md) · [AddressSanitizer](tools/ios-performance.md#5-addresssanitizer--범위-밖-접근해제-후-사용-같은-메모리-손상을-테스트가-도는-동안-잡아내는-컴파일러-기능)

### Main Thread Checker

UI API를 메인 스레드 밖에서 부르는 실수를 실행 중에 찾는 Xcode의 진단 도구입니다. 켜 둔 채 성능을 재면 검사 비용이 측정값에 섞일 수 있으므로, 끄거나 켜지 않은 시나리오를 따로 둡니다.

관련 문서: [측정 함정](03-performance.md) · [ThreadSanitizer](tools/ios-performance.md#6-threadsanitizer--동기화-없이-두-스레드가-같은-메모리에-접근하는-데이터-경합을-테스트가-도는-동안-찾는-컴파일러-기능)

### Release·Debug 빌드

Debug 빌드는 디버깅하기 쉽게 컴파일러 최적화를 끈 개발용 빌드이고, Release 빌드는 최적화를 켠 배포용 빌드입니다. 같은 입력이라도 Debug에서는 몇 배 느릴 수 있으므로, 사용자 체감은 실기기 Release 빌드의 값으로 말합니다.

관련 문서: [검증 원칙과 해석 원칙](01-principles.md) · [성능 검증](03-performance.md)

### SBOM

Software Bill of Materials의 줄임말로, 제품에 들어간 구성 요소(라이브러리와 버전) 목록입니다. 안전 판정이 아니라, 새 취약점이 공개됐을 때 영향을 받는지 바로 확인하는 근거로 씁니다.

관련 문서: [보안 검증](04-security.md) · [cdxgen과 CycloneDX](tools/common-security-quality.md#5-cdxgen과-cyclonedx--앱에-무엇이-들어-있는지-표준-형식의-목록으로-남기는-도구)

### XCFramework

Apple 플랫폼용 라이브러리를 여러 플랫폼·아키텍처별로 미리 빌드해 한 묶음으로 배포하는 형식입니다. 바이너리로 들어오므로 새니타이저 검사 코드가 들어가지 않고, 그 안의 라이브러리는 의존성 감사가 읽는 lockfile(의존성 버전을 고정해 적어 둔 파일)에도 나타나지 않습니다.

관련 문서: [보안 검증](04-security.md) · [osv-scanner](tools/common-security-quality.md#3-osv-scanner--의존성-목록을-공개-취약점-데이터베이스와-대조하는-도구)

### xcresult

Xcode가 테스트를 실행한 뒤 남기는 결과 묶음(`.xcresult`)입니다. 테스트 성패·로그·커버리지·첨부 파일이 들어 있고, 스크립트에서는 `xcresulttool`·`xccov`로 필요한 부분을 꺼냅니다.

관련 문서: [XCTest](tools/ios-testing.md#3-xctest--xcode의-기본-테스트-프레임워크이자-ui-테스트성능-측정과-결과-번들xcresult의-기반) · [xccov](tools/ios-testing.md#5-xccov--xcresult의-코드-커버리지를-타깃파일함수줄-단위로-읽는-xcode-명령행-도구)
