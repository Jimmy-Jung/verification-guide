# Q4 유지보수 — CI 게이트와 자동화

## 차례
- 커버리지 게이트
- 복잡도 분포
- CI 게이트 분할 기준
- 수동 실행 잡
- 시간에 민감한 검사
- 브랜치 보호 확인
- 보고서 문구

## 커버리지 게이트

- 모듈별 기준을 둔다. 모든 입력이 지나가는 핵심 모듈(파서·코어)에 더 높은 기준(예: 90%), 전체에 낮은 기준(예: 80%). 핵심 모듈이 호스트·JVM에서 빠르게 테스트되면 높은 기준을 유지하기 쉽다.
- 같은 소스가 여러 테스트 번들에 정적 링크되면 커버리지 보고서에 중복으로 나타난다. **파일별 최댓값**을 쓴다(`scripts/coverage_gate.py`가 이 규칙을 따른다).
- CI가 돌리지 않는 테스트(에뮬레이터 계측 등)를 합친 값과 CI 기준값을 구분해 적는다.
- 한계: 줄이 실행됐다는 뜻이지 결과가 맞는지 검사했다는 뜻이 아니다. 높은 커버리지에서도 플랫폼 간 비교(패리티)·퍼징(fuzz 테스트)이 결함을 많이 찾는다. 커버리지는 "테스트가 닿지 않은 곳"을 찾는 지표로 쓴다.
- 기준값의 근거를 스크립트 상수 주석과 보고서에 적는다. 근거 없는 숫자를 두지 않는다.

## 복잡도 분포

- 함수별 순환 복잡도(lizard)·규모(scc)·스타일 위반(린터)을 모은다.
- 평균 대신 **분포**를 본다. 중앙값과 임계값(예: 16) 이상 함수 수·최댓값.
- 가장 복잡한 함수 한두 개는 왜 복잡한지(분기 원인)와 어떤 검증이 그 경로를 지나는지(퍼징 플랫폼 간 비교·회귀 테스트 입력) 적는다. 설명하지 않은 나머지 함수 수도 적는다.
- 복잡도·줄 수·lint는 관리 부담의 경향이지 결함 수가 아니다.

## CI 게이트 분할 기준

기준은 **빠르고 결정적인가**. 커밋 검사의 실패가 코드 문제를 안정적으로 가리켜야 병합 판단에 쓸 수 있다.

| 커밋마다(자동) | 릴리스 전(수동 잡) |
|---|---|
| 빌드, 공용 입력 모음(코퍼스) 해시 검사, 단위 테스트(퍼징 1만 회 포함), 커버리지 게이트, 정적 분석, 의존성 감사 | 실기기 성능, 퍼징 10만 회, 에뮬레이터 계측 테스트, 데모 UI·접근성 테스트, 최소 OS 실행 |

- 공유 가상 머신에서 실행마다 다른 이유로 실패하는 UI 테스트(WebView 초기화·접근성 감사·입력 지연 시간 초과)는 로컬 통과를 확인한 뒤 수동 잡으로 옮기고, 그 대가로 커밋마다 잡히지 않는 회귀를 보고서에 적는다.
- CI가 고르는 OS(설치된 최신 시뮬레이터)와 최소 OS 전용 결함의 재현 조건을 구분한다.
- 새 push가 진행 중 실행을 취소하는 설정(`cancel-in-progress`)이면 그 사실을 적는다.

## 수동 실행 잡

`workflow_dispatch` 입력(예: `ui_tests`)으로 켜는 잡을 둔다. 무엇이 수동인지, 마지막으로 언제 어떤 커밋에서 돌렸는지 검수 기록에 남긴다.

## 시간에 민감한 검사

CI 게이트의 의미를 유지하면서 환경 지연에 덜 흔들리게 한다. 입력당 상한을 넘으면 같은 입력을 3회 다시 재서 가장 빠른 값으로 판정하고, 세 번 다 넘으면 실패. 이 완화는 결함 대장에 T 항목으로 기록한다.

## 브랜치 보호 확인

CI 실패가 병합을 **강제로** 막는지 확인한다(`gh api repos/<o>/<r>/branches/main`의 `protected`, ruleset). 보호가 없으면 "현재는 사람이 실패 상태를 보고 판단하며 강제 게이트가 아니다"라고 적는다.

## 보고서 문구

- "커밋마다 도는 CI 게이트"와 "릴리스 전 수동 검사"를 그림 하나로 그리고, 저장소별 차이(의존성 감사가 한쪽만 자동 등)를 캡션에 적는다.
- 테스트 수는 규모 변화를 보여 주지만 플랫폼 간 세는 방식이 달라 서로 비교하지 않는다.
