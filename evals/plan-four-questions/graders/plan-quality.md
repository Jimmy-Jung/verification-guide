검증 계획이 다음을 갖추면 PASS, 하나라도 빠지면 FAIL.

1. 검증을 네 가지 질문(오류·성능·보안·유지보수, 또는 같은 뜻의 분류)으로 나누고, 질문마다 구체적인 방법을 붙였다. 예: 오류에는 공용 입력 코퍼스·두 구현 비교(차등 테스트)·시드 고정 퍼즈·극단(병리) 입력 중 둘 이상, 성능에는 실기기 Release 반복 측정, 보안에는 위협 모델과 공격 입력, 유지보수에는 CI 게이트·커버리지 기준.
2. "작성 주체(AI)가 아니라 결과(입력에서의 동작)를 검증한다"는 관점을 한 문장 이상으로 밝혔다.
3. 계획이 재실행 가능한 형태(스크립트·CI·게이트)를 포함하고, 커밋마다 돌릴 검사와 릴리스 전 수동 검사를 구분했거나 구분하겠다고 했다.
4. "확인하지 않은 범위" 또는 "남은 조건"을 보고서에 적겠다고 했거나, 미확인 항목을 명시했다.
5. 사용자가 결정해야 할 항목(예: 실기기 확보, 도구 설치, 결함 수정 범위, 퍼즈 규모, 보고서 양식)을 모아서 물었다.

단위 테스트 몇 개 추가 같은 일반론만 있고 위 구조가 없으면 FAIL. 형식(표·목록)은 판정에 쓰지 않는다.
